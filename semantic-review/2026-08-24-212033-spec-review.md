# Auth Rate Limits, Challenge Cleanup, and Persistent Audit Events — Spec Review

This spec adds three hardening layers to the EarnProof auth stack: a Redis-backed rate limiter enforced via NestJS guards, a scheduled cron job that prunes stale `WalletChallenge` rows in bounded batches, and a fire-and-forget `AuditService` writing privacy-safe `AuditLog` rows for every significant auth outcome.

**Watch for:** (1) The `AuditLog` schema uses `actorId` as a foreign key to `User.id` — but the spec writes `sha256(walletAddress)` there, which will fail FK constraints on every write; because the write is fire-and-forget, failures are silently swallowed and audit events never land. This is a blocking correctness issue that requires a schema change the spec claims isn't needed. (2) `@Cron(this.cronExpression)` is evaluated at class-definition time before the constructor runs — `this.cronExpression` will be `undefined` and the job will never register. (3) The `HashedClientKey` is defined in requirements as an optional component of rate-limit keys but is completely absent from the design and tasks. (4) The INCR+EXPIRE algorithm is labeled "sliding-window" but is actually a fixed-window counter with a race at the window boundary.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The rate-limit layer uses INCR+EXPIRE, which is a fixed-window counter — not a sliding window as the spec claims. The window resets on the first hit within the window, and two concurrent first-requests will both see `count === 1`, both set TTL, and effectively start the counter at 2. For `limit=1` this means the limit is unenforced during the race. The design should name the algorithm correctly and acknowledge the race so operators understand the enforcement semantics.

The `AuditLog` Prisma model has `actorId String?` as a FK to `User.id`. Writing `sha256(walletAddress)` — a 64-character hex string — into that field will trigger a FK violation on every insert. The `.catch()` in `write()` will swallow every failure silently. The spec says no schema change is needed; a schema change is required. The fix is adding a separate `actorHash String?` column (no FK) or dropping the relation from `actorId`.

`@Cron(this.cronExpression)` in `ChallengeCleanupService` doesn't work: NestJS decorators resolve at class definition time, so `this.cronExpression` is always `undefined`. The cron job will fail to register or throw at startup. The design needs to specify the correct pattern — dynamic registration via `SchedulerRegistry.addCronJob()` in `onModuleInit`.

`HashedClientKey` is introduced in the requirements glossary and appears in Requirement 1.1 as an optional second component of the rate-limit key. The design and every task use only `sha256(walletAddress)`. Either the language needs to be removed from Requirement 1.1 or the design needs to describe how client metadata is extracted and hashed.

The default values for all seven new variables are declared in both `env.validation.ts` (Zod `.default()`) and `configuration.ts` (`?? value`). Any future change must be made in two places. The spec instructs repeating this pattern — worth deciding whether to fix the drift risk at the same time as adding seven more instances of it.

Task 10.1 (wire `auth.module.ts`) lists `RateLimitService`, `RateLimitGuard`, `AuditService`, and `ChallengeCleanupService` as providers to add, but `RateLimitGuard` injects `AuditService` — if `AuditService` isn't registered before the guard is instantiated, NestJS will throw. The provider list in 10.1 is correct but the task description should note the injection dependency so it isn't accidentally reordered or omitted.

<details>
<summary>Issues (7)</summary>

1. **AuditLog FK violation on every write** — `AuditLog.actorId` is a FK to `User.id` in the Prisma schema, but the spec writes `sha256(walletAddress)` (a hex string) there. Every `prisma.auditLog.create()` will throw a FK violation that is silently swallowed by `.catch()` — audit events will never persist. The schema must change: add a separate `actorHash: String?` column (no FK) for the hashed address, or remove the `@relation` from `actorId`. Update Requirements 5.6/5.7, the design data model table, and all three `AuditService` method payloads. The spec's "no Prisma schema changes are needed" claim is incorrect.

2. **`@Cron(this.cronExpression)` evaluated before constructor runs** — NestJS decorators resolve at class definition time; `this.cronExpression` is `undefined` when `@Cron()` reads it. The cron job will not register correctly. Fix by using `SchedulerRegistry.addCronJob()` in `onModuleInit` to register the job after config is available, or by accepting the expression as a constructor argument via a factory provider. Task 6.1 needs to describe the chosen pattern in detail.

3. **INCR+EXPIRE race window at window open** — two concurrent requests on an empty key both INCR to 1, both call `expire`, and the counter starts at 2. For `limit=1` the limit is unenforced during this window. The spec also mislabels this as "sliding-window" when it is a fixed-window counter. The design should name the algorithm correctly and document the concurrent-first-request behavior explicitly.

4. **`HashedClientKey` defined in requirements but absent from design and tasks** — Requirement 1.1 specifies optionally combining the wallet key with a hashed client metadata value. Nothing in the design or tasks implements or defers this. Either remove the optional-combination language from Requirement 1.1 (and the `HashedClientKey` glossary entry) or add a design section and task covering which header to extract, how to handle absent headers, and how to combine the two hashes.

5. **Default values duplicated between `env.validation.ts` and `configuration.ts`** — the spec instructs adding Zod `.default()` values in `env.validation.ts` and `?? value` fallbacks in `configuration.ts` for all seven new variables. A future change to any default must be made in two places and can silently drift. Either route the Zod-validated env object into `configuration.ts` or remove the `?? fallbacks` in `configuration.ts` and rely solely on Zod. Tasks 1.1 and 1.2 should reflect whichever pattern is chosen.

6. **`logLoginFailed` for `rate_limited` has no `resourceId`** — the RateLimitGuard fires before any challenge is fetched, so no `challengeId` is available. The audit row will have `resourceType: 'WalletChallenge'` but a null `resourceId`, unlike the `invalid_signature` and `challenge_unavailable` paths which always supply one. Requirement 5.5 doesn't mention `resourceId` for this case — the design should explicitly note the asymmetry so implementers don't try to populate a field that doesn't exist at guard-time.

7. **`ioredis` and `@nestjs/schedule` absent from `package.json`** — neither package appears in `dependencies`. Tasks.md mentions installing them but gives no pinned versions. Given the project pins other packages (e.g., `@nestjs/swagger: 11.4.6`), the spec should specify exact versions or version ranges for both and confirm they belong in `dependencies` (not `devDependencies`).

### AuditLog schema conflict with hashed actorId

The existing `AuditLog` model in `prisma/schema.prisma`:

```prisma
model AuditLog {
  actorId  String?
  actor    User?    @relation(fields: [actorId], references: [id])
  ...
}
```

`actorId` is a FK: it must be a valid `User.id` (cuid) or null. The spec's `AuditService` writes `sha256(walletAddress)` — a 64-character hex string — into this field. PostgreSQL will reject every insert with a FK violation. Because `write()` is fire-and-forget and the `.catch()` only logs, the application starts normally but no audit event ever persists. The spec's "no Prisma schema changes are needed" is incorrect — confirmed by reading the schema directly.

One clean fix: add `actorHash String?` with no relation to `AuditLog`, store the hashed wallet address there, and use `actorId` (the FK column) only when the actor is a known `User`. This requires updating the design's data model table, Requirements 5.6/5.7, all three `AuditService` method payloads, and the property tests for Properties 8 and 9.

### Rate-limit algorithm: fixed-window counter, race at limit=1

The INCR+EXPIRE pattern is a fixed-window counter: the window starts on the first request and expires after `windowSeconds`. This is not a sliding window. For a 60-second window with limit 5, a user can make 5 requests at T=59s, let the window expire at ~T=119s, and immediately make 5 more — 10 requests in roughly 60 seconds. Acceptable for most abuse-prevention goals, but operators need to understand the semantics.

The race: two concurrent requests on an empty key both INCR to 1. Both then call `expire` — the second is a no-op since the key exists. The counter is now at 2 with the correct TTL, but the limit wasn't enforced for those two requests. For `limit=1` this means one extra request always slips through on a fresh window. The design should explicitly name this "fixed-window with concurrent-first-request tolerance of 1" so the team can decide whether to address it with a Lua script or accept it.

### `@Cron` decorator and dynamic cron expressions

NestJS's `@Cron()` decorator from `@nestjs/schedule` is a TypeScript method decorator evaluated at class registration time — before any constructor runs. `this.cronExpression` doesn't exist at that point. The pattern in the design will receive `undefined` as the cron expression.

The standard fix is `SchedulerRegistry.addCronJob()` called from `onModuleInit`:

```typescript
async onModuleInit() {
  const job = new CronJob(this.cronExpression, () => this.runCleanup());
  this.schedulerRegistry.addCronJob('challenge-cleanup', job);
  job.start();
}
```

Task 6.1 should describe this pattern in full, including the `SchedulerRegistry` injection and the `CronJob` import from `cron`.

### HashedClientKey gap between requirements and design

Requirement 1.1 specifies: "hashing the wallet address with `sha256()` and **optionally combining it with a hashed client metadata value**, producing a HashedWalletKey that contains no raw IP address." The design keys exclusively on `sha256(walletAddress)`. No task mentions client metadata extraction.

If client-metadata bucketing is deferred, Requirement 1.1 should be reworded to say the key is derived solely from `walletAddress`, and the `HashedClientKey` glossary entry should be removed or marked future. If it is in scope, the design needs to answer: which header is used (`X-Forwarded-For`, `CF-Connecting-IP`), what happens when the header is absent, and how the two hashes are combined into one Redis key.

### 429 body retryAfter not pinned in guard tests

Task 3.5 verifies the guard throws 429 and calls `AuditService.logLoginFailed` with `reason: 'rate_limited'`, but doesn't verify that the `retryAfter` value in the response body equals `RateLimitResult.retryAfter`. A hardcoded `retryAfter: 30` in the guard would pass all the described tests while breaking the contract for any client that uses `retryAfter` to back off. Task 3.5 or 9.2 should include an assertion that `response.body.retryAfter === mockResult.retryAfter`.
