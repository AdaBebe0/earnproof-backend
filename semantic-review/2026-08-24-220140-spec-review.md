# Spec Review: Auth Rate Limits, Challenge Cleanup, and Persistent Security Audit Events

## Executive Summary

The spec is **not yet ready for implementation** due to two blockers. The pinned `@nestjs/schedule@4.1.2` is peer-incompatible with the project's NestJS 11 stack and will produce a broken install. The task wave graph places the Prisma migration (task 8.3) in wave 6, after `AuditService` (wave 3) writes to the column that migration creates — meaning the code won't compile until the implementer manually re-sequences the steps. Everything else — the DI graph, graceful degradation design, privacy guarantees, and migration safety — is sound.

**Verdict: NEEDS_CHANGES**

Watch for: `@nestjs/schedule` version pin is wrong for NestJS 11; migration task 8.3 must move to wave 0 or 1.

---

## High-level view

The three-layer design (RateLimitService, ChallengeCleanupService, AuditService) maps cleanly onto the existing module structure. The DI graph is consistent: `AuditService` needs only `PrismaService` (global) and `Logger`; `RateLimitService` needs only `REDIS_CLIENT` and `ConfigService` (both global). `RateLimitGuard` injecting `AuditService` works because both live in the same `AuthModule` provider scope.

The `configuration.ts` description in the spec is a mismatch with the existing file. The spec says to read from "the already-validated environment object produced by `env.validation.ts`" without `??` fallbacks. The actual `configuration.ts` reads `process.env` directly with inline `??` defaults — it is a plain factory function and never receives the Zod-validated object. An implementer following the spec literally will reference a variable (`env`) that isn't in scope.

`@nestjs/schedule@4.1.2` declares peers `@nestjs/common: ^8.0.0 || ^9.0.0 || ^10.0.0`, which excludes the project's `^11.1.9`. NestJS 11 support starts at `@nestjs/schedule@5.0.0`. The task notes should be updated to pin `5.0.1` or `6.1.3`.

The task wave graph places the Prisma migration (task 8.3, wave 6) after `AuditService` is coded (task 5.1, wave 3). `AuditService` references `actorHash` on `auditLog.create` — a field that doesn't exist in the generated Prisma client until the schema is updated and the client is regenerated. The TypeScript compiler will reject the service file until 8.3 runs. Moving 8.3 to wave 0 unblocks the rest of the implementation sequence.

The raw wallet address privacy claim is genuine for the scope of this change. `sha256()` is applied before every Redis key write and every `AuditLog` field population. The existing `WalletChallenge.walletAddress` and `User.walletAddress` columns are pre-existing and out of scope.

<summary>Issues (6)</summary>

1. **`@nestjs/schedule` version pin incompatible with NestJS 11** — `@nestjs/schedule@4.1.2` declares `@nestjs/common: ^8.0.0 || ^9.0.0 || ^10.0.0` as a peer, excluding the project's `^11.1.9`. npm will report an unresolvable peer conflict. Minimum compatible version is `5.0.1`; current latest is `6.1.3` (both declare `^10.0.0 || ^11.0.0`). Update the tasks notes pin.

2. **Prisma migration mis-sequenced in task wave graph** — Task 8.3 (add `actorHash` column, regenerate client) sits in wave 6. `AuditService` (task 5.1, wave 3) calls `prisma.auditLog.create({ data: { actorHash: ... } })`. Until 8.3 runs and the client is regenerated, `actorHash` is not a known field on `auditLog.create` and TypeScript compilation fails. Move 8.3 to wave 0 or wave 1.

3. **`configuration.ts` pattern mismatch** — The spec instructs task 1.2 to read from the "already-validated environment object" without `??` fallbacks. The existing `configuration.ts` is a factory that reads `process.env` directly and applies its own `??` defaults — it never receives the Zod output. An implementer following the spec description will reference `env.AUTH_CHALLENGE_RATE_LIMIT_MAX` in a scope where `env` doesn't exist. The spec should describe the `process.env.AUTH_CHALLENGE_RATE_LIMIT_MAX ?? 10` pattern matching the file, or explicitly introduce the refactor needed to thread the validated object into the factory.

4. **`logRateLimited` ghost method in design prose** — The design's Error Handling table lists `logRateLimited` and the `AuthService Integration` section calls `AuditService.logRateLimited()`. No such method exists in the `AuditService` interface — the correct call is `logLoginFailed({ reason: 'rate_limited', ... })`. Task 3.4 has it right; the design prose does not. Fix the error handling table row and the integration section to match the interface.

5. **`CHALLENGE_CLEANUP_INTERVAL_CRON` not validated as a legal cron expression** — The field uses `z.string()` with no format check. An invalid expression passes startup validation and throws at runtime inside `onModuleInit()` when `new CronJob(expr, cb)` is called. The spec should either add a `z.string().refine(isCronValid, ...)` using the `cron` package's validator, or explicitly acknowledge that cron validation is deferred to service initialization.

6. **`resourceType = "WalletChallenge"` on rate-limit events is semantically misleading** — Requirement 5.5 and the field mapping table specify `resourceType = "WalletChallenge"` for rate-limited rejections even though no challenge has been fetched at that point and `resourceId` is null. A future audit query filtering on `resourceType = 'WalletChallenge'` will return rate-limit events mixed with actual challenge events, with no way to distinguish them except by checking `action`. Consider `resourceType = null` or a dedicated value, or add an explicit note in the requirement acknowledging the tradeoff.

<summary>Details</summary>

### `@nestjs/schedule` version pin targets the wrong NestJS generation

`@nestjs/schedule@4.1.2` declares `peerDependencies: { "@nestjs/common": "^8.0.0 || ^9.0.0 || ^10.0.0" }`. The project runs `@nestjs/common@^11.1.9`. npm will report an unresolvable peer conflict on install — confirmed by checking the published package metadata directly. NestJS 11 support begins at `@nestjs/schedule@5.0.0` (peer range `^10.0.0 || ^11.0.0`). The `ioredis@5.6.1` pin has no peer constraint issue and is correct.

### Prisma migration sequencing

The spec's task wave graph:

```
wave 3: 3.2, 5.1, 6.1    ← AuditService coded here
wave 4: 3.3, 3.4, 5.2, 6.2  ← AuditService tested here
wave 6: 8.2, 8.3, 9.1, 10.1, 10.2  ← migration runs here
```

`AuditService.write()` calls `prisma.auditLog.create({ data: { actorHash: sha256(...), ... } })`. Until task 8.3 adds `actorHash String?` to the schema and the Prisma client is regenerated, `actorHash` is not a recognized field on `auditLog.create` and the TypeScript compiler will reject the `AuditService` file. The build script runs `prisma generate` before `nest build`, so the schema update and generate step must precede any code that touches the new field. Task 8.3 belongs in wave 0.

### `configuration.ts` pattern conflict

The existing `configuration.ts`:

```typescript
export const configuration = () => ({
  redisUrl: process.env.REDIS_URL,
  appUrl: process.env.APP_URL ?? "http://localhost:3000",
  // ...
});
```

This is a plain factory. `ConfigModule.forRoot({ load: [configuration], validate: validateEnv })` runs `validateEnv` separately to validate the environment and then runs `configuration()` to build the config object. The two functions don't share state — the factory never receives the Zod-parsed output. The spec's task 1.2 description instructs the implementer to omit `??` fallbacks because "defaults are already set by Zod `.default()` in `env.validation.ts`." That reasoning is correct for `env.validation.ts` itself, but `configuration.ts` reads `process.env` directly — not the Zod output — so it has no access to Zod's coerced defaults. The correct implementation is `process.env.AUTH_CHALLENGE_RATE_LIMIT_MAX ? Number(process.env.AUTH_CHALLENGE_RATE_LIMIT_MAX) : 10`, which matches the existing file pattern.

### Ghost method reference: `logRateLimited`

Two locations in the design reference a non-existent method:

- Error Handling table: `Rate limit exceeded → HttpException(429) + logRateLimited`
- AuthService Integration section: `The guard calls AuditService.logRateLimited() before throwing 429`

The `AuditService` interface specifies `logLoginFailed({ walletAddress, reason: 'rate_limited' })`. Task 3.4 has the correct call. The design prose has a stale name that will send an implementer looking for a method that doesn't exist.

### Cron expression validation gap

`CHALLENGE_CLEANUP_INTERVAL_CRON` uses `z.string()` with no format constraint. The `cron` package (a dependency of `@nestjs/schedule`) exposes `CronTime.validateExpression()` or equivalent that can be used in a Zod `.refine()`. Without it, a misconfigured cron string silently passes the startup validation check and causes `ChallengeCleanupService.onModuleInit()` to throw, leaving cleanup silently disabled with no startup-time indication of the misconfiguration.

### `resourceType = "WalletChallenge"` on rate-limit events

Requirement 5.5 sets `resourceType = "WalletChallenge"` for rate-limited rejections. At the point the guard fires, the challenge hasn't been fetched — `resourceType` is being set to a model name with no corresponding row. Any downstream audit query filtering `WHERE resourceType = 'WalletChallenge' AND resourceId IS NULL` will return both genuine challenge-not-found failures and rate-limit rejections together. The `metadata.reason` field differentiates them, but the `resourceType` label creates a semantic mismatch that will surprise future query authors. This is a requirements-level decision and should be documented as deliberate, or changed to a value like `null` or `"RateLimit"`.

## Confirmed Resolved

- **`actorHash` vs `actorId` field separation** (confirmed): The `AuditEventPayload` interface, field mapping table, and all three `AuditService` method specs correctly set `actorId` only for `auth.login.success` events with a known `userId`, and leave it null for all others. The privacy boundary between the hashed-wallet identifier and the FK is consistent throughout.

- **Redis graceful degradation** (confirmed): `enableOfflineQueue: false` causes the ioredis client to fail immediately rather than queue. The `try/catch` in `RateLimitService.check()` returns `{ allowed: true }` on any Redis error. The chain from Requirements 1.6 / 2.4 through to the implementation is complete end-to-end.

- **`actorHash` migration is additive and zero-downtime** (confirmed): The existing `AuditLog` schema has no `actorHash` field, no unique constraint that would be violated, and no FK relationship that would be affected. Adding `actorHash String?` with a new composite index is a safe additive migration.

- **`SchedulerRegistry` / programmatic cron** (confirmed): The design correctly explains why `@Cron(this.cronExpression)` doesn't work and specifies the `SchedulerRegistry.addCronJob()` alternative. This is the right approach for config-driven cron expressions.

- **`sha256` utility reuse** (confirmed): Both `RateLimitService` and `AuditService` are directed to use `src/common/crypto/hash.ts`. No reimplementation is introduced.

- **Fixed-window race condition disclosed** (confirmed): The ±1 burst tolerance at window boundaries is called out explicitly in the design.

- **`REDIS_URL` already validated** (confirmed): `env.validation.ts` has `REDIS_URL: z.string().min(1)` — no additional validation needed.
